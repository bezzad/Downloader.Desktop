## Context

`Services/PluginManager` already supports three ingredients this design reuses rather than reinvents:
- Loading any DLL from a folder into a collectible `AssemblyLoadContext`, with the SDK assembly forced to
  resolve from the host (`PluginLoadContext`).
- A built-in tier (`LoadBuiltIns()` → `AppContext.BaseDirectory/plugins`, disable-only) and a user tier
  (`LoadFromDirectory(PluginsRoot)` → `~/.config/Downloader/plugins`, removable) — these are *folders*, not
  compiled-in references. Built-ins are only "built-in" because the app's own build copies plugin project
  outputs into its own publish folder; nothing at the loader level distinguishes them.
- `Services/UpdateService`, which already checks `GET /repos/{owner}/{repo}/releases/latest`, compares a
  semver-ish version, finds a named asset, downloads it via the engine, and relaunches — the exact shape
  needed for optional-plugin install/update, just pointed at a different asset.

`Downloader.Plugins` (external repo) has git tags but no GitHub Releases, so there is currently no artifact
an app could fetch even if it tried. This design's release-pipeline half exists to produce that artifact;
the app-side half exists to consume it through the existing user-plugin loading path.

## Goals / Non-Goals

**Goals:**
- One repo holds all first-party plugin source (built-in and optional), one release event produces both
  the app's own archives and every optional plugin's archive + a machine-readable catalog.
- Optional plugins are structurally incapable of bloating a fresh install: no `ProjectReference`, no
  build-output copy step from the app project to any optional plugin project.
- Installing/updating an optional plugin never loads unverified bytes: sha256 is checked before extraction.
- The Hls plugin's YouTube/x.com resolution bug is fixed as part of the migration (not deferred).

**Non-Goals:**
- A decoupled release cadence for plugins (hotfix a plugin without cutting an app release). Explicitly
  rejected per the proposal's accepted trade-off — every plugin update rides on an app `vX.Y.Z` tag.
- Plugin code signing / Authenticode-style trust chain. sha256-against-a-manifest-we-publish is the bar for
  this change; true signing is a future hardening step if a real third-party ecosystem ever emerges.
- Rebuilding the Torrent plugin fully — scaffolding only, if time allows, per the proposal.
- Any change to how built-in plugins load, update, or are toggled — that path is already correct.

## Decisions

### D1: Optional plugins are separate `.csproj`s in this solution, excluded from the app's publish output
`Downloader.Desktop.Plugins.Hls.csproj` is added to `Downloader.Desktop.sln` for build/test purposes only.
The app's `.csproj` gets **no** `ProjectReference` to it, and the MSBuild target that stages built-ins into
`plugins/` (currently keyed off the `Downloader.Desktop.Plugins.GitHub`/`.Ollama` outputs) is **not**
extended to include it. A solution-level test (or a simple CI assertion: `dotnet publish` output must not
contain `Downloader.Desktop.Plugins.Hls.dll`) guards this so the isolation can't silently regress.
- **Alternative considered**: keep Hls out of the `.sln` entirely, build it via a standalone `dotnet build`
  step in CI. Rejected — it forfeits IDE discoverability and shared `Directory.Build.props`/SDK versioning
  for no real isolation benefit; a missing `ProjectReference` already gives the guarantee that matters.

### D2: Catalog manifest is a release asset, not a new endpoint or a file on `main`
`plugins-catalog.json` is generated by the release workflow and uploaded as an asset on the **same**
`vX.Y.Z` release as the app archives — not committed to `main` (would need a bot-commit step and drifts
from what's actually installable) and not a separate hosted endpoint (no infra to run one). The app fetches
it via the identical `releases/latest` call `UpdateService` already makes, so there is exactly one
"what's current" source of truth: the latest GitHub Release.
- **Alternative considered**: per-plugin GitHub tags (`plugin-hls-v1.2.0`) with their own release objects.
  Rejected per the proposal's explicit decision to piggyback on the app's existing release cadence instead
  of standing up a second tag/release scheme.

### D3: Install/update reuses the user-plugin folder and loader, not a new plugin class
An installed optional plugin is placed in `PluginManager.PluginsRoot` and loaded via the existing
`LoadFromDirectory` path — from the loader's perspective it is indistinguishable from a plugin a user
dropped in by hand via "Install plugin...". `PluginDescriptor.IsBuiltIn` stays `false`. This means Remove
already works with zero new code; only Add (fetch + verify + place + reload) and Update-check are new.

### D4: Verification is sha256-before-extract, computed over the downloaded archive
The catalog entry's `sha256` is checked against the downloaded zip's hash before any file inside it is
written to `PluginsRoot`. On mismatch: delete the temp download, surface a friendly error ("couldn't verify
the plugin download, please try again"), do not touch the plugins folder. This is a hard gate, not a
warning — matches the proposal's "reject and show a friendly error on mismatch."

### D5: Update flow mirrors `MainViewModel`'s existing self-update toast, not a modal
Consistent with how the app already tells the user about its own updates (background check → actionable
toast → user-accepted download → swap), an optional-plugin update follows the same shape: background
version compare against the catalog on the same cadence/trigger as the app's own check, a toast per
outdated plugin, accept → download/verify/swap via `RemovePlugin` + re-`LoadFromDirectory`. No auto-update.

### D6: HLS bug fix ships as part of the migrated project, not a follow-up
The YouTube/x.com pure-video-link fix (whatever branch/state exists on `Downloader.Plugins`, e.g.
`feat/video-site-extraction`) is brought over and verified as part of moving the project, so the migrated
`Downloader.Desktop.Plugins.Hls` is correct from its first commit in this repo rather than reproducing a
known-broken state that then needs a second fix pass.

## Risks / Trade-offs

- **[Risk] Rebuilding every optional plugin on every app release adds CI time and surface area to the
  release workflow.** → Mitigation: plugin projects are small (one today); parallelize the new jobs
  alongside the existing per-platform app build matrix rather than serializing after it.
- **[Risk] A plugin update is coupled to an app release — an urgent plugin-only fix still requires bumping
  the whole app version.** → Mitigation: explicitly accepted (Non-Goal); this repo already cuts patch
  releases cheaply and often, so the cost is low in practice.
- **[Risk] git-history preservation for the Hls migration (subtree/filter-branch) can fail or be messy on a
  from-scratch attempt.** → Mitigation: attempt `git subtree`/`git filter-repo` first; if it produces a
  broken or unreasonably large graft, fall back to a clean copy of current source + tests (history stays
  recoverable from the old repo until it's deleted, so nothing is lost either way).
- **[Risk] `dotnet publish` accidentally starts copying the Hls project into the app output later (e.g. a
  future dev adds a convenience `ProjectReference`) and silently reintroduces the dependency the whole
  design exists to avoid.** → Mitigation: the CI assertion from D1 fails the build if the Hls assembly
  appears in the app's publish output.
- **[Risk] sha256 verification adds a failure mode (mismatch) users will hit if a release asset is ever
  corrupted at rest.** → Mitigation: the failure is a clear, retryable error, not a crash or a silently
  loaded bad DLL — the whole point of the gate.

## Migration Plan

1. Bring `Downloader.Plugins.Hls` source + tests into `src/Downloader.Desktop.Plugins/Downloader.Desktop.Plugins.Hls`, apply the YouTube/x.com fix, get it green standalone (mirrors the "loadability" test pattern already used for GitHub/Ollama).
2. Wire it into `Downloader.Desktop.sln` (build/test only) and confirm the app's publish output does not include it.
3. Extend `release.yml` with the optional-plugin build/zip/hash/catalog jobs; dry-run against a draft/test tag before it affects a real release.
4. Add app-side catalog fetch, Add/verify/install, and update-check + toast, reusing `UpdateService`'s pattern and `PluginManager`'s existing folder/loader.
5. Manually verify against `add-video-site-extraction`'s blocked task 7.3 (paste a YouTube/x.com URL, confirm it downloads and plays) before either change is archived.
6. Author confirms end-to-end; only then does repo deletion of `Downloader.Plugins` happen, manually, outside this change.

No rollback beyond normal git revert is needed pre-release; post-release, an optional plugin install/update
failure only affects the optional plugin (verified before load, and Remove already works), never the core
app or built-ins.

## Open Questions

- Preserve `Downloader.Plugins`' git history in the move, or accept a clean copy? (Design defaults to
  "try subtree/filter-repo, fall back to clean copy" — author can override before task 1 starts.)
- Exact trigger/cadence for the optional-plugin update check — same app-startup check as `UpdateService`,
  or only on-demand when the user opens Settings → Plugins? (Design assumes "same cadence as the app's own
  check" per D5; confirm during implementation if that feels too chatty.)
